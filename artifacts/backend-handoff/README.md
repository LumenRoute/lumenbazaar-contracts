# Backend Handoff Artifacts

Synthetic, machine-readable fixtures that the backend and the contracts must
agree on. Nothing here contains secrets, production records or real user
accounts.

| File | Purpose |
| --- | --- |
| `encoding-vectors.v1.json` | Versioned cross-repository encoding vectors generated by Rust. |
| `encoding-vectors.lock.json` | Compatibility lock: version, file and SHA-256 of every published vector file. |
| `encoding-vectors.CHANGELOG.md` | One entry per published vector version. |
| `domain-separation-v3.json` | Interface v3 domain-separated session ID and usage commitment example. |
| `usage-receipt-v1.schema.json` | Usage receipt v1 schema. |
| `usage-receipt-v1.fixtures.json` | Usage receipt v1 canonical encoding fixtures. |
| `usage-hashes.example.json` | Usage hash examples. |

## Encoding compatibility vectors

`encoding-vectors.v<N>.json` is produced by
`contracts/upto-session/src/encoding_vectors_test.rs` from the contract's own
encoding code (`ids.rs`, `events.rs`, `validation.rs`) and the Soroban XDR
serializer. Rust is the source of truth. The file contains:

- `version`, `schema`, `interfaceVersion` and the `rules` it covers;
- `networkPassphrases`: Unicode, empty and length-boundary passphrases with
  UTF-8/UTF-16 lengths, NFC flag, backend acceptance and `network_id`;
- `sessionIds`: inputs, preimage XDR and session ID, including sequence, amount
  and expiry extremes and NFC/NFD-derived network IDs;
- `usageCommitments` and `usageReceipts`: usage hash preimages and canonical
  receipt bytes, plus invalid receipts with an error category;
- `addresses`, `amounts`, `resourceHashes`: valid encodings (ScVal XDR) and
  invalid inputs with an error category, plus the `create_session` result and
  `ContractError` code where the contract decides;
- `sessionExpiry`: duration boundaries around `MAX_SESSION_DURATION_LEDGERS`;
- `events`: topic and data XDR for the create, settle, cancel and extend events
  with the expected typed decoding.

Notable rules (the full list is in the file):

- `network_id = sha256(passphrase UTF-8)` with no normalization. NFC and NFD
  forms of the same visible text produce different IDs, so producers reject
  non-NFC input instead of normalizing it.
- Passphrases are non-empty, NFC, without surrounding whitespace and at most 256
  UTF-16 code units.
- Amounts are canonical base-10 strings that fit `i128`; `create_session`
  rejects values `<= 0` with `InvalidAmount`.
- The all-zero resource hash is encodable but rejected with `InvalidResourceHash`.

### Commands

```bash
# Rust: regenerate in memory and fail if the committed file is stale
cargo test -p upto-session --all-features encoding_vectors

# Rust: intentionally rewrite the current version's file
LUMENBAZAAR_UPDATE_ENCODING_VECTORS=1 cargo test -p upto-session --all-features encoding_vectors

# Backend (TypeScript): verify the same file and the compatibility lock
npm --prefix bindings/upto-session run build
node --test scripts/lib/encoding-vectors.test.mjs
node scripts/check-encoding-vectors.mjs --base origin/develop
```

CI runs all three checks. The backend verifier uses the generated binding's
`deriveSessionId`, `canonicalizeUsageReceipt` and `hashUsageReceipt` helpers and
the Stellar SDK it re-exports. It does not sign or submit transactions.

### Compatibility gate

Published vector files are immutable:

1. `encoding_vectors_match_committed_artifact` fails when the contract encoding
   or the generator no longer reproduces the committed file.
2. `encoding_vectors_are_pinned_by_compatibility_lock` fails when the committed
   file does not match the SHA-256 pinned for its version in
   `encoding-vectors.lock.json`, or when the changelog has no `## v<N>` entry.
3. `scripts/check-encoding-vectors.mjs --base <PR base>` fails when a version
   that exists on the base branch is edited or removed.

Regenerating the current file after an encoding change therefore fails CI until
the change is published as a new version.

### Deliberate encoding change

1. Bump `ENCODING_VECTORS_VERSION` in `encoding_vectors_test.rs`.
2. Run the regenerate command. It writes `encoding-vectors.v<N+1>.json` and leaves
   the previous file untouched.
3. Add a `"<N+1>"` entry to `encoding-vectors.lock.json` with the new file's
   SHA-256 and status `current`, set `current` to `N+1`, and change the previous
   entry's status to `retained` (still verified) or `retired` (kept for audit,
   no longer verified).
4. Add a `## v<N+1>` entry to `encoding-vectors.CHANGELOG.md` describing the
   change and the backend migration.
5. Update `docs/backend-integration-handoff.md` and the root `CHANGELOG.md`.

Retention policy: published files are never deleted or rewritten. Retiring a
version only stops verification; it cannot be reactivated.
