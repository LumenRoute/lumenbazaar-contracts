# Policy Wallet Invariants

> **Example code. Not audited. Not production ready.** These properties raise confidence in the
> example's spending rules. They do not make the policy wallet suitable for custody of real funds.
> See [Residual example-only risks](#residual-example-only-risks).

The properties are in `src/property_test.rs` and run against the real contract. Each generated case
creates a random policy (caps from 1 to `i128::MAX`, authorization limits from 1 to `u32::MAX`,
random seller, asset, and resource allowlists with optional per-seller and per-resource limits, and
a validity window that may not have started, may be open, or may end within a few ledgers). It
then runs up to 23 `check_payment` and optional `authorize_payment` calls, with ledger jumps of
zero, one, a few, or exactly to one ledger before, at, or after the next day boundary. Amounts
include 0, 1, -1, `i128::MIN`, `i128::MAX`, the payment cap, the payment cap plus one, the
remaining daily allowance, and random values. Sellers, assets, and resources include one entry that
is never allowlisted. A reference model of the documented rules predicts every result.

All addresses are generated by the test host and all resource hashes are synthetic constants.

## Invariants

| ID | Invariant | Proved by |
| --- | --- | --- |
| P1 | An authorized payment is positive and never exceeds the policy per-payment cap, or the per-seller or per-resource per-payment cap when one applies. | `p1_p2_p3_p5_p6_p7_random_policies_hold_every_invariant` |
| P2 | Cumulative authorized spend within one ledger day never exceeds the daily cap (policy, per-seller, and per-resource), and the authorization count never exceeds `max_authorizations_per_day`, across arbitrary sequences. | `p1_p2_p3_p5_p6_p7_random_policies_hold_every_invariant` |
| P3 | `check_payment` never mutates state, and a rejected `authorize_payment` never mutates state. The whole wallet instance storage is compared as XDR before and after each call. | `p1_p2_p3_p5_p6_p7_random_policies_hold_every_invariant`, `p5_degenerate_policies_are_rejected_without_state_change` |
| P4 | Day rollover is deterministic. The ledger day is `sequence / LEDGERS_PER_DAY` (17,280). Spend and authorization counts reset at the first ledger of a new day, not one ledger earlier or later, and identical policy, ledger, and inputs always give identical results and totals. | `p4_day_rollover_is_pinned_at_the_boundary`, `p4_identical_inputs_give_identical_results` |
| P5 | A payment is authorized if and only if every constraint passes: validity window (inclusive at both ends), positive amount, payment cap, seller, asset, and resource allowlists, daily authorization count, daily cap, and per-seller and per-resource limits. The first failing constraint is reported, in that order. Degenerate policies are rejected at `set_policy`. | `p1_p2_p3_p5_p6_p7_random_policies_hold_every_invariant`, `p5_validity_window_is_inclusive_at_both_ends`, `p5_degenerate_policies_are_rejected_without_state_change` |
| P6 | `check_payment` and `authorize_payment` agree in the same state: if the check rejects, authorization rejects with the same error, and if authorization succeeds, the check passed. | `p1_p2_p3_p5_p6_p7_random_policies_hold_every_invariant` |
| P7 | Extreme amounts (0, -1, `i128::MIN`, `i128::MAX`, values that would overflow the running total) never panic or overflow. Every call returns `Ok` or a defined `PolicyWalletError`. | `p1_p2_p3_p5_p6_p7_random_policies_hold_every_invariant`, `p7_extreme_amounts_return_defined_errors` |

The scenario tests in `src/test.rs` and the mutation harness remain unchanged and keep pinning the
documented examples in [policy-examples.md](policy-examples.md).

## Running and reproducing

```bash
cargo test -p policy-wallet-example property_harness
```

The random properties use proptest with fixed seed `0x4c554d45504f4c49` and 64 cases (16 for the
determinism property), so CI and local runs generate the same inputs. On failure proptest shrinks
the case and prints the minimal `PolicySpec` and `Step` sequence. To reproduce:

1. Rerun the same command. The fixed seed regenerates the same failing case.
2. Copy the printed minimal input into a new `#[test]` that calls `run_case(&spec, &steps)`, so the
   failure becomes a permanent regression test.

Run a larger campaign locally (still deterministic for a given count):

```bash
LUMENBAZAAR_POLICY_CASES=1024 cargo test -p policy-wallet-example property_harness -- --nocapture
```

On PowerShell:

```powershell
$env:LUMENBAZAAR_POLICY_CASES = "1024"
cargo test -p policy-wallet-example property_harness -- --nocapture
Remove-Item Env:LUMENBAZAAR_POLICY_CASES
```

## Residual example-only risks

This wallet is an **example**. It is **not audited**, **not production code**, and must not hold
or authorize real funds. The properties above say nothing about the following:

- **Key management.** Owner and agent keys, their storage, rotation, and compromise recovery are out
  of scope. A compromised agent key can spend up to every cap, every day, until the owner replaces
  the policy.
- **No custody link.** `authorize_payment` only records spend. Nothing forces a payment to go
  through it, and nothing ties an authorization to a specific `upto-session` settlement. Callers must
  enforce that.
- **Replay across deployments.** Policies and spend records are per contract instance. Another
  deployment of this wallet has independent counters, so the same agent can spend each cap again on
  each deployment.
- **Ledger-time assumptions.** Days are ledger-sequence buckets of 17,280 ledgers, not calendar days.
  Their wall-clock length depends on ledger close times and drifts. A "day" boundary can be crossed
  by waiting, so an agent can spend two daily caps within seconds around a boundary.
- **Storage lifetime.** All policies and spend counters are in instance storage, and in this
  version nothing extends its TTL. If the instance is archived the wallet stops working until
  restored, and restoration is not guaranteed. Daily counters are never pruned, so instance storage
  grows with every day an agent is active.
- **Policy updates and governance.** `set_policy` replaces a policy immediately. There is no delay,
  multi-party approval, or revision check against concurrent updates, and replacing a policy keeps
  the day's recorded spend.
- **Front-running and ordering.** Authorizations are evaluated in transaction order. Concurrent
  authorizations near a cap race; only cap enforcement is guaranteed, not fairness or priority.
- **Token contract trust.** Asset allowlisting compares addresses only. The wallet does not verify
  token behavior, decimals, or whether the asset is a reviewed contract.
- **Authorization model.** Tests use mocked authorization. Real signing, nonce handling, and
  authorization entry construction are not exercised here.
- **No formal verification.** Properties are sampled with bounded case counts. They are evidence,
  not proof, and do not cover inputs the generators cannot produce.
